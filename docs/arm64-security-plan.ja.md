# ARM64解析対応と運用改善の作業計画

作成日: 2026-09-18  
調査基準: `cd8ebbf06badc5dc599aea3d3898d0f5e221d447`  
状態: 計画。以下の完了条件は、実装・検証済みであることを示さない。

具体的な編集・検証方法は[作業手順書](arm64-security-runbook.ja.md)にまとめる。
着手時に基準コミットとの差分を確認し、変更された実装に合わせて本計画を更新する。

## 1. 目的と決定事項

今回の対象は、全体の依存削減、運用時の誤認を減らす改善、InspectorのARM64対応である。
AuditorのRPC検査とWardenのプロセス単位のOS制限という責務分担を維持する。

### プロジェクト全体の原則

Pure Rustの追求と依存の最小化は、ディスアセンブラだけでなく、
CLI、ポリシー処理、Auditor、Warden、Inspector、ビルド・テスト支援を含む
プロジェクト全体へ適用する。[開発方針](development.md#dependency-and-ffi-policy)にも
同じ原則を記載する。

- 機能・正確性・セキュリティ上の保証・対応環境・性能の維持を必須条件とする。Pure Rust化や依存削減のための後退は認めず、FFI案にも同じ条件を適用する。
- 標準ライブラリと既存依存の再利用を先に検討し、必要に応じて小規模なRust実装または最小限のPure Rust依存を選ぶ。独自実装にも同じ品質・性能条件を課す。
- 直接依存だけでなく、推移的依存、重複バージョン、feature、OS別依存、build/dev依存、ネイティブライブラリ・ツールも確認し、不要なものを減らす。
- FFIは最後の手段とする。Rustで要件を満たせない具体的な根拠と、FFI案が要件を満たす証拠を必要とする。実装が楽、コード量が少ないという理由だけでは選ばない。
- Rustラッパーや静的リンクを使っても、C実装への依存をPure Rust扱いしない。OS固有機能に必要な既存バインディングも必要性と範囲を確認し、保証を維持する最小限の境界に閉じ込める。
- 測定条件と測定誤差の判定方法を先に定め、性能低下を依存削減との交換条件にしない。未検証や条件未達は未完了として残し、要件を引き下げて完了にしない。

### 今回の対応方針

| 対象 | 採用する方針 |
|---|---|
| 全体の依存 | D1で使用箇所・有効な依存グラフ・featureを棚卸しし、機能・性能を維持できる不要・重複依存の削減を実施する |
| dry-run | 実際にサーバーを起動し、OS隔離を無効化して違反ツール呼び出しも転送すること、副作用があることをヘルプに明記する |
| OSごとの保証範囲 | RPC検査とOS制限を分け、適用範囲、非対応設定、拒否・警告・未適用の挙動を一覧化する。SBPLの保守上の制約も説明する |
| 診断 | 確定できるAuditor拒否・サンドボックス設定失敗と、原因が確定できない子プロセスのエラーを区別する |
| パス検証 | 正規化関数の単体テストに加え、Auditorの判定対象と子プロセスが実際に開いたファイルを比較する |
| ディスアセンブラ | 全体原則を適用し、P4でPure Rust案を先に検証する。要件を満たせずCapstoneが満たせる場合に限りFFIを採用する。iced-x86は当初維持し、x86解析の比較検証後に置換可否を決める |
| 解析対象 | Linux AArch64 ELFを先に追加し、続いてmacOS ARM64 Mach-OとDarwin ABIを追加する |
| 解析結果 | 未対応・解析不能・部分解析と、解析した範囲での検出0件を区別し、出力とポリシー生成まで伝える |

ここでいうARM64はAArch64を指す。ARM端末上でmcp-writが動くことと、
ARMの機械語をInspectorが解析できることは別の対応項目として扱う。
既存のARM向け配布ターゲットだけでは、後者の対応や実機検証を証明できない。

ディスアセンブラにも上記の原則を適用し、FFIは要件達成に不可欠な場合だけ許容する。
現時点で「Capstoneだけが要件を実現できる」とは確認できていない。
`yaxpeax-x86` / `yaxpeax-arm` に命令効果の処理を補う案も比較対象とする。
段階導入では `iced-x86 + yaxpeax-arm` も評価できるが、それだけで
iced-x86の代替を検証したことにはならない。

CapstoneはFFIが必要になった場合の候補であり、スライサーで利用する
レジスタアクセスや命令グループの情報を取得するAPIがある。
[Capstoneの詳細情報API](https://docs.rs/capstone/latest/capstone/struct.InsnDetail.html)と、
[yaxpeax-armの命令表現](https://docs.rs/yaxpeax-arm/latest/yaxpeax_arm/armv8/a64/struct.Instruction.html)を
起点に、採用版ごとの情報取得と必要な補完実装を確認する。
APIの存在だけで完全性を保証せず、どちらも同じfixtureと期待値で検証する。

P4では、既存x86の解析精度と性能、AArch64の番号追跡、未知の命令効果の扱い、
対象環境での構築と依存の増減を比較する。単に命令をデコードできるだけでも、
すべてを未解決にして誤判定を避けるだけでも要件を満たしたとは扱わない。
自前実装が必要という理由だけでPure Rustを不可能とせず、補完範囲と保守負担も記録する。
Pure Rust案が同じ要件を満たせれば優先し、満たせない具体的な根拠と
Capstone側の適合結果が揃った場合にFFI採用を確定する。
以下のP5〜P7はCapstoneを選んだ場合の実装案とし、Pure Rustを選んだ場合は
バックエンド固有の手順を更新する。形式・ABI・解析状態の設計と受け入れ条件は共通とする。
速度・バイナリサイズ・解析精度の優劣は、測定前に結論づけない。

**P4選定結果（実施済み）**: Pure Rust案を採用する。x86-64はyaxpeax-x86への
置換を行わず、既存のiced-x86を `src/inspector/decoder/x86.rs` の薄い内部IF越しに維持し、
AArch64は `yaxpeax-arm` 0.4系を選定した（解析配線はP5）。
Capstone（capstone 0.14 / capstone-sys 0.18）は不採用:
同一入力評価でデコードギャップ後の再同期に失敗してsyscallサイト自体を
見失うケース、暗黙レジスタ書き込み情報の欠落（自前補完表が必要）、
同一条件で約2桁以上のスループット低下、配布全ターゲットへのCツールチェーン
要件が確認された。FFIが不可欠という根拠は成立しなかった。
P5〜P7の「Capstoneで〜」手順は yaxpeax-arm の `src/inspector/decoder/` 配下
バックエンドへ読み替える。形式・ABI・解析状態の設計と受け入れ条件は
変更しない。詳細は [結果記録](arm64-security-results.ja.md) のP4節を参照。

## 2. 現状の根拠と維持する境界

| 現状 | 主な確認先 | 計画への影響 |
|---|---|---|
| dry-runのヘルプはログと転送の説明だけで、OS隔離無効化の記載がない | [CLI定義](../src/cli/parse_run.rs)、[起動処理](../src/runtime/launch.rs) | noargsのヘルプを修正する。clapへの移行は不要 |
| OS制限は起動時にプロセスへ適用する | [Warden](../src/warden/mod.rs)、[Linux起動](../src/warden/linux_spawn.rs) | ツールごとのメモリ・ファイルシステム分離を保証しない |
| パスを検査しても、通常は元のRPCを転送する | [パス解決](../src/pathutil.rs)、[要求検査](../src/auditor/checker.rs)、[転送](../src/auditor/proxy_c2s.rs) | 検査と実アクセスの同一性を原子的に保証したとは扱わない |
| 命令解析とスライス処理がiced-x86に依存する | [disasm](../src/inspector/disasm.rs)、[slicer](../src/inspector/slicer.rs) | 単純な依存置換では足りず、命令の副作用と停止条件の移植が必要 |
| 非x86-64 ELFのsyscall解析が空の配列になる | [profile](../src/inspector/profile/mod.rs) | ARM追加前に「未対応」と「0件」の表現を分離する |
| 現在のsyscall番号表はLinux x86-64用 | [syscall_table](../src/inspector/syscall_table.rs) | 命令セットとOS/ABIを分けて番号表を選ぶ |
| ELFを前提にシンボル・セクション・文字列を解析する | [elf_parser](../src/inspector/elf_parser.rs)、[text_section](../src/inspector/text_section.rs)、[strings](../src/inspector/strings.rs) | Mach-Oの入力処理を追加する。既存のgoblinを継続利用する |
| 人間向け・JSON・KDL出力と生成ポリシーが解析結果を利用する | [出力](../src/inspector/profile/format.rs)、[生成](../src/legislator/policy_generator.rs) | 未解析の情報を下流で消さない。出力互換性も検証する |

既存の[README](../README.ja.md)と[ポリシー作成ガイド](policy-authoring.ja.md)には、
プロセス単位の制限やdry-runの注意点がすでにある。
今回のドキュメント作業は、それらとCLI・OS別の説明を整合させる作業とする。

維持する条件:

- OSに与えた権限は同一サーバープロセス内で共有される。ツール間の隔離が必要な運用では、プロセス・サーバー・ポリシーの分割を案内する。
- 未対応設定の扱いは実装ごとに記載する。「すべて拒否される」と一括して説明しない。未対応OSの警告付き非隔離起動なども確認対象に含める。
- dry-runでも、設定に応じたツール定義の遮断検査は残る。すべての検査が無効になるとは説明しない。
- `EPERM` / `EACCES` だけではWardenが原因だと断定しない。OS拒否の一般的な傍受機能は今回追加しない。
- Landlockの拒否ログを「許可しながら記録する監査モード」と扱わない。seccompのログ設定変更をdry-runの代替として導入しない。
- stdoutのJSON-RPC、監査ログの既存契約、検証から起動までの順序、子プロセスの終了・資源解放を維持する。[既存の不変条件](modules.md)も適用する。

各段階を独立してレビュー・差し戻しできる変更単位にする。
日数は、実機・Cツールチェーンの確保とP4の試作結果を確認してから見積もる。

| ID | 作業・成果物 | 前提 | 完了条件 |

| P0 | 基準状態、既存テスト、機能・性能・依存の基準値、実行環境を記録 | なし | 対象HEAD、変更前の挙動・測定条件、OS/CPU/ツール版、未検証項目が特定できる |
| D1 | プロジェクト全体の依存を棚卸しし、不要依存・feature・重複を削減 | P0 | 削減前後の有効な依存グラフと、機能・性能・保証を維持した証拠がある。残す依存の用途と理由が分かる |
| P1 | dry-runヘルプと日英ドキュメントの整合 | P0 | 実行・OS隔離無効化・違反転送・残存する遮断検査・副作用が明確 |
| P2 | OS別の保証範囲、SBPL依存、トラブルシュートを整理 | P0 | 各項目に実装根拠と非対応時の挙動があり、検証済みOS版を区別できる |
| P3 | 診断の分類と実アクセス比較テスト | P1、P2 | 誤った原因断定がなく、パス判定と実アクセスの一致・不一致を再現可能に記録できる |
| P4 | Pure Rust案の要件適合と、必要な場合のCapstoneを検証し、解析基盤を導入 | P0、D1の棚卸し | 機能・性能を維持する選定根拠が残り、未対応を0件扱いしない。FFI採用時は不可欠な理由と対象環境での成立性が確認できる |
| P5 | Linux AArch64 ELF解析 | P4 | 命令位置・番号・ABI・未解決理由を検証し、生成ポリシーまで正しく反映できる |
| P6 | Mach-OとDarwin ARM64解析 | P5 | thin/fatの各slice、Darwinの番号体系、インポート経由の検出と解析限界を区別できる |

基本の着手順はP0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8とする。
D1はP0後に開始し、棚卸し結果をP4の選定へ渡す。削減は小さな変更単位で進め、
P8で全体の依存差分と退行がないことを確認する。
P4以降はP3と実装上は独立しているため、担当や環境が分かれる場合は先行できる。
ヘルプ・ドキュメント改善をARM対応の完成まで待たせる必要はない。

## 4. 設計上の確定事項と実装時に詰める点

### 4.1 解析対象と解析状態

解析対象を少なくとも「ファイル形式、命令セット、エンディアン、OS/ABI、
対象slice、解析したコード範囲」で識別する。実行ホストの`cfg(target_arch)`で
入力バイナリのデコーダやsyscall番号表を選ばない。

ELFの`EM_AARCH64`だけではLinux ABIと確定できない。
ABIを判別する根拠や明示指定の方法を決め、曖昧な場合は番号をLinuxの名前に
無条件で変換しない。Mach-Oでも対象プラットフォームとCPU subtypeを記録し、
macOS ARM64以外まで対応済みとは扱わない。

解析状態は少なくとも次を区別する。具体的な型名・出力フィールド名はP4で決定する。

| 状態 | 意味 |
|---|---|
| 解析実施 | 明示したコード範囲を解析した。検出0件でも、バイナリ全体の安全を意味しない |
| 部分解析 | 一部の命令、セクション、slice、ABI解釈などを扱えなかった |
| 未対応 | 形式・命令セット・ABIが対応外 |
| 非適用 | インタープリターのソース解析など、ネイティブ命令解析の対象ではない |
| 失敗 | 破損入力、境界不正、デコーダ初期化失敗など |

シンボル・文字列・syscallの各解析状態も保持する。
人間向け出力、JSON、KDL、リスク表示、`generate-policy`まで伝播させる。
既存の数値スコアは安全性の証明に使わず、不完全な解析を単に「低リスク」と
表示しない。変更が既存出力の利用者へ影響する場合は移行ガイドを更新する。

### 4.2 デコーダとスライサー

必要最小限の内部インターフェースを用意し、命令長・位置・オペランド、
レジスタの読み書き、制御フロー、syscall入口を扱う。
命令の効果が分からない状態を、レジスタを書き換えない状態と区別する。
すべてのCPU命令を共通の巨大な中間言語へ移植することは目的にしない。

Capstone採用時は詳細情報を有効化し、必要なx86/ARM64機能に依存を絞る。
使用するcrate・同梱Cライブラリ・feature・ライセンスを記録する。
Rustラッパーを通じたFFIの利用はデコーダ内部に閉じ込め、
バックエンド固有の型や生ポインターをAuditor・Warden・ポリシー層へ持ち出さない。
不完全なアクセス情報、未知命令、分岐、呼び出し、部分レジスタ書き込みで
古い値を誤って採用しないよう、未解決で停止する条件を先に実装する。

### 4.3 ABIとMach-O

| 対象 | 主に検証する入口 | 注意点 |
|---|---|---|
| Linux x86-64 | `syscall`、`rax` | 現在の部分レジスタ・暗黙書き込み・制御フロー処理を維持 |
| Linux AArch64 | `svc #0`、番号は`w8` | `w8/x8`の関係と定数構築を検証。x86の番号表を流用しない |
| Darwin ARM64 | `svc #0x80`、一般的な入口で`x16` | Unix syscallとMach trapを分け、符号や番号体系を正しく保持 |

命令入口の規約だけで全呼び出しを検出できるわけではない。
Mach-OではlibSystem等のラッパー経由のアクセスもあるため、
インポートやシンボルの分類を合わせて扱う。間接呼び出し・動的ロード・
共有ライブラリ内部を追跡できない範囲は明記する。

fat/universal入力は、各sliceの対象と解析状態を別々に出力する。
初期対応外のx86-64 Darwinやarm64e等が含まれても、黙って捨てたり、
全sliceを解析できたような集約をしたりしない。
Darwinの番号・名称をLinux seccomp用の許可リストへ混入させない。

### 4.4 パス比較の範囲

実ファイルを使い、同じRPC入力について次の証拠を対応付ける。

1. Auditorが解決した対象と許可・拒否理由。
2. 子プロセスへ転送された入力と、その作業ディレクトリ。
3. 開いたハンドルから得たファイル識別情報、または識別用内容と結果。

正常系、静的な解釈差、同期を取ったsymlink差し替え、プロセス共通権限の
境界を分けて検証する。不一致が見つかった場合は、修正可能な誤判定と
設計上の制約を分けて記録する。
テストの合格をTOCTOUの不存在や任意サーバーの安全性の証明としない。

## 5. 検証環境と採否条件

| 環境 | 必要な証拠 |
|---|---|
| Linux x86-64 | 既存解析の回帰、Landlock/seccompの強制実行、診断・パス比較 |
| Linux AArch64 | ネイティブビルド・実行、AArch64解析、同OSのWarden動作 |
| macOS Apple Silicon | ARM64 Mach-O解析、SBPLの生成・実適用、パス比較 |
| macOS x86-64 | 既存配布ターゲットのビルド・起動と既存機能の回帰 |
| Windows x86-64 | C依存のビルド、他ISAのfixture解析、LPAC・パス比較の回帰 |
| Windows ARM64 | 配布ビルドのリンク確認。実機実行が未実施なら、その範囲を明示 |
| Linuxコンテナ | C依存追加後のCLI/runnerとコンテナE2E。配布対象ごとの互換性を確認 |

ビルド成功、クロスコンパイル、fixtureの静的解析、実機でのOS強制テストは
別々に記録する。環境不足によるskipは合格に数えない。
GitHub Actionsのrunner名だけではCPUやOS版を保証せず、実際の値を記録する。
手動実行・Releaseから呼び出す既存のワークフロー方針を維持する。

iced-x86削除を含むすべての依存変更では、機能・性能・保証の後退がないことを
採否条件とする。解析では、差分を説明でき、誤った「解決済み」が増えず、
従来正しく解決できたケースと検出範囲を維持し、全配布ターゲットで構築できる必要がある。
同一条件で測定誤差を超える性能後退があれば採用しない。
両ライブラリの一致だけを正しさの根拠にせず、命令仕様に基づく期待値と比較する。
条件を満たせなければiced-x86の削除は見送る。併用を選ぶ場合も、
要件を満たすために両方が必要な理由を示し、不要な比較用依存は残さない。

## 6. 対象外・リスク・切り戻し

今回の対象外は、ツールごとのOS隔離、動的な権限昇降、eBPF導入、
ARM32/Thumb、Windows PE解析、任意シェルコードの安全性証明、
全システムコールの実行時追跡、SBPL利用の新しい同意フラグである。
実装中に必要性が判明した拡張は、今回の必須条件へ無断で追加しない。

| リスク | 対処 |
|---|---|
| 依存削減やPure Rust化で機能・性能が後退する | 変更前の基準と比較し、後退する案は採用しない。必要な依存を残す根拠を記録する |
| CapstoneのCビルドやリンクが既存配布を壊す | P4で早期に確認し、採用版・feature・クロスツールチェーンを固定する |
| デコーダ変更で番号を誤解決する | 仕様から作った期待値と両実装の比較を使い、未知の効果は未解決にする |
| Mach-O/ABI対応が膨らむ | 対応sliceとコード範囲を限定して明示し、未対応を消さない |
| 診断がWarden原因だと誤誘導する | 確定した段階だけを表示し、errnoやstderrは補助情報として扱う |
| SBPLがOS更新で動かなくなる | 検証したOS版と再確認手順を残し、非対応・適用失敗を明示する |
| 日本語ドキュメントが破損する | UTF-8・BOM・LFを確認し、問題が疑われる場合は編集前にバックアップする |

問題のある新規バックエンドは、その入力を未対応・部分解析と明示する状態へ
戻せるよう変更を分割する。解析失敗を「検出0件」に戻したり、
OS制限を無効化してリリース条件を満たしたりしない。
切り戻しは該当変更だけを対象とし、既存のユーザー変更を破棄しない。

## 8. 一次資料

参照日: 2026-09-18。実装時には採用バージョンに対応する資料を確認する。

- [Capstone Rust binding](https://github.com/capstone-rust/capstone-rs)と[同梱Cライブラリのビルド](https://github.com/capstone-rust/capstone-rs/blob/master/capstone-sys/build.rs): 採用版・feature・ビルド方式の確認先。
- [Capstoneのレジスタアクセス情報](https://www.capstone-engine.org/op_access.html): 命令効果の取得方法。Rust APIの挙動は別途実測する。
- [yaxpeax-x86](https://github.com/iximeow/yaxpeax-x86)と[yaxpeax-arm](https://github.com/iximeow/yaxpeax-arm): Pure Rust候補。デコード範囲と、スライサーに必要な補完処理を確認する。
- [goblinのMach-O解析](https://docs.rs/goblin/latest/goblin/mach/index.html): 既存パーサー依存を利用する際の確認先。
- [Linux syscall ABI](https://man7.org/linux/man-pages/man2/syscall.2.html): x86-64/AArch64の入口とレジスタ規約。
- [Apple XNUのsyscallラッパー](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/custom/SYS.h)と[ARM Mach trap](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/arm/syscall_sw.h): Darwin解析の根拠。対象版の出典をfixtureにも残す。
- [Apple DTSのsandbox-execに関する説明](https://developer.apple.com/forums/thread/661939): サードパーティー向けにサポートされたAPIとは扱えないことの根拠。
- [Landlock](https://docs.kernel.org/userspace-api/landlock.html)と[seccomp filter](https://docs.kernel.org/userspace-api/seccomp_filter.html): OS機構の制約。現行コードが使用するABI・設定との差も確認する。
