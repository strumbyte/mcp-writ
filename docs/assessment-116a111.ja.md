## 必ず維持する前提

- 主計画は、利用者が扱うOS固有事項を減らし、導入・設定・実効制御の把握を容易にすることです。
- **各OSの公式・標準のサンドボックスを利用できることは必須です。既存のネイティブ実行・サンドボックス対応を維持します。**
- **microVMを含むVM隔離は追加の隔離手段です。導入を理由に既存のOSサンドボックス経路を削除したり、既存制御を暗黙に無効化したりしません。**
- 過度な共通化は目的にしません。全OSの実行方式をLinuxへ統一することは前提にせず、OSごとに適切な起動・隔離実装を選びます。
- ホスト側とゲスト側のどこで、どのサンドボックスが効くのかを明示します。VMを起動しただけで、ホストのプロセス制限がゲストへ引き継がれたとは扱いません。
- 複数の実行パターンを製品の前提として扱います。ネイティブ実行、既存イメージの利用、ソースからのコンテナ化を、一つの実行形態だけで評価しません。
- 手動CIの方針、応答内容のDLPとHTTP/SSEを別レイヤーとする境界は維持します。
- 可視化によって誤認を解くことと、権限を分離して攻撃経路をなくすことを区別します。テスト失敗件数を製品欠陥数には置き換えません。

macOSの現行実装は `sandbox-exec` / SBPLです。OSが提供する機構であることと、第三者向けの安定した公開・サポートAPIであることは区別します。この点は既存ガイドに注意書きがあるため、他OSと同等のサポート保証があるように記述せず、ネイティブ経路を維持したうえで扱いを明示します。

根拠: [OSごとのWarden](guide.md)（21行）、[macOSのサポート上の注意](guide.md)（696行）。

## A1. 保護の単位はプロセス

### 現状

Linuxでは、許可ツールのファイル権限が既定の権限とともにプロセス共通のLandlockルールへ合流します。侵害されたサーバーや、呼び出し引数に現れない内部処理も、実際にOS層で許可された範囲を利用し得ます。

`exec_shell` の拒否はRPC検査です。OS層で許可されている `execve` まで拒否するものではありません。

### 方針・完了条件

起動前に、既定権限・許可ツールの権限・実行に必要な権限を含む、OS層の適用予定を示します。起動時に確認できた適用状態はB2で区別します。ツールの設定を単純に一覧化しただけで「実際の全権限」と断定しません。

読み取りツールと、書き込み・ネットワーク等の権限を持つツールが同一プロセスにあることを、構成レビューで判断できる状態にします。現在のランナーでツールごとのカーネルサンドボックスは作りません。

解消する問題は、ツール別の許可がOS層でもツールごとに分離して適用される、という誤認です。同一プロセス内の権限共有は改善後も残り、可視化と構成レビューによって受容する境界として扱います。

根拠: [Landlockルール構築](../src/warden/landlock_impl.rs#L18)、[許可ツールの権限合流](../src/warden/landlock_impl.rs#L133)、[OS別の制御範囲](guide.md)（698行）、[README](../README.md)。

## A2. ツール別の許可・引数検査と、MCP全体の通過規則

### 現状

ツール別の許可・引数検査は `tools/call` に限られます。`tools/list` の定義検証と `notifications/tools/list_changed` に伴う再検証は別に存在します。

`resources/read` と `prompts/get` はクライアント起点の要求であり、現状ではメソッドの許可リストによる制限を受けず転送されます。サーバー自身がその要求を処理する場合、OS層で許可された範囲がアクセス可能範囲の上限になります。

`2025-11-25` のサーバー起点RPCも転送されます。`2026-07-28` では `sampling/createMessage` などの追加要求が `input_required` 応答内の `inputRequests` に入り、その応答はそのまま転送されます。

戻ってきた `inputResponses` を拒否しても、クライアント側ですでに行われた処理は取り消せません。クライアント側の処理は、サーバー子プロセスのOSサンドボックスでは制限できません。

### 方針・完了条件

対応版、通信方向、要求・応答・通知ごとに通過規則を定義します。旧版のサーバー起点RPCと、新版の応答内追加要求の両方を対象にします。

- 未定義の要求・追加要求は既定で拒否し、通過・拒否の判断と理由を監査に記録します。
- `2025-11-25` の `notifications/initialized`、`2026-07-28` の判定に使う `server/discover` を含め、対応版の通信手順を維持します。
- キャンセル、進捗、ツール一覧の変更通知の扱いを定義します。通知は要求と同じ応答処理にしません。
- `method` のない応答は許可済み要求との対応で扱います。単なるメソッド名の許可リストだけで全通信を判定しません。
- 仕様上の制御フィールドと、任意の応答内容を区別します。

解消する問題は、ツール呼び出し以外の要求・追加要求について、通過してよい範囲がポリシーで明示されていないことです。改善後も任意の応答内容のDLPは対象外であり、クライアントが実行済みの処理の取り消しも保証しません。

根拠: [要求検査](../src/auditor/checker.rs#L210)、[サーバー側からの転送](../src/auditor/proxy_s2c.rs#L47)、[対応版の説明](guide.md)（657行）、[MCP 2025-11-25 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)、[MCP 2026-07-28 MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)。

## A3. 固定の範囲と、同一性を確認する時点

### 現状

ファイル単位の照合と、イメージ単位の固定は別です。

`binary-hash` と `entrypoint-hash` は、指定ファイルの内容と、起動実行ファイルまたは最初のペイロード引数との対応を検査します。`lockfile-hash` / `docker-manifest-hash` だけでは、`run` の起動対象を結び付けられません。

`python -m` や `npx` でも、インタープリターやランチャーのハッシュ固定は可能です。結び付けられないのは、それらが選択する実行対象本体です。インライン評価はハッシュ指定がある場合に拒否されます。

スクリプトの内容は起動前の初回照合でハッシュします。起動直前の再検証では実行ファイルを再ハッシュしますが、別ファイルのスクリプトは引数とのパス対応を確認するだけで、内容を再ハッシュしません。検証から読み込みまでファイルを不変に保持する仕組みもありません。

一方、`run-image` は既定でイメージダイジェストを要求します。イメージ内の依存先を一律に未固定とは扱いません。解析では依存ライブラリ名やインポートシンボルを抽出しますが、依存先の実体を再帰的に解析・ハッシュ固定するものではありません。

### 方針・完了条件

固定対象、検証時点、検証後に変更可能な範囲を宣言します。対応する起動形にはネイティブ実行ファイル、スクリプトファイル、イメージダイジェストを残します。

保証範囲を広げる場合は、venvや `node_modules` 等の依存先を識別・固定する方式と、実行時の可変性を合わせて検討します。VM隔離ではゲストカーネル等の実行基盤の版・構成も別途明示します。

今回は解析の網羅性拡大より、固定範囲と保証の明確化を優先します。これは優先順位の判断であり、解析範囲の拡大に効果がないという評価ではありません。

解消する問題は、ハッシュしたファイルが実行コード全体であり、検証後も常に同一であると読めることです。固定対象外から加わるコードと検証後の変更は、保証範囲に含める仕組みを実装・確認しない限り残ります。

根拠: [起動対象の照合・再検証](../src/verifier/hash.rs#L250)、[起動順](../src/runtime/launch.rs#L97)、[イメージダイジェストの要求](../src/container/runner.rs#L72)、[解析範囲](../src/inspector/macho_parser.rs#L3)。

## A4. 混乱した代理人の説明と、一般化に必要な規則

### 現状

機能は既定でオフです。有効時も対象名は `list_files`、`list_directory`、`read_file` に固定されています。それ以外の名前には、この機能固有の検査は適用されません。

一覧取得とファイル読み取りは、どちらも `read_only` になり得ます。`side_effect` だけでは、パスを発見する処理と利用する処理を区別できません。

同じ子プロセスを共有するクライアントは `known_paths` を共有します。この制約は本文に記載済みですが、構成図と攻撃表は任意機能であることが読み取りにくい状態です。

### 方針・完了条件

図・攻撃表・本文で、既定オフ、対象となる操作、プロセス単位の共有状態という説明を揃えます。

一般化を実装する場合は、操作の役割と、引数・応答からパスを抽出する規則を定義します。説明修正と役割対応は二者択一にしません。役割対応だけではクライアント間の状態分離は実現しません。

解消する問題は、限定的な任意機能が常設の一般的な保護に見えることです。既定オフとプロセス単位の状態共有を維持する場合は、改善後も明示すべき境界として残します。

根拠: [名前による分岐](../src/auditor/proxy_c2s.rs#L289)、[共有状態の前提](../src/auditor/session.rs#L88)、[本文の説明](guide.md)（665行）、[攻撃表](guide.md)（87行）。

## A5. OS標準サンドボックスを維持したVM隔離の追加

### 合意済みの位置づけ

各OSのネイティブサンドボックスを利用できることを維持し、追加の隔離手段としてmicroVM等を導入します。VM隔離はホストとの境界を強化する拡張であり、A1〜A4の代替策ではありません。

| OS | 維持する現行のOS層 | 追加隔離の候補と決定状況 |
|---|---|---|
| Linux | Landlock、seccomp、no_new_privs | Kata Containers対応を計画に含める |
| macOS | 現行のsandbox-exec / SBPLによるネイティブ経路。サポート範囲の注意書きも維持 | Apple公式のcontainer / Containerizationを対応候補として検証する |
| Windows | AppContainer、Job Object、DACLによる制御 | Hyper-V分離のWindowsコンテナを優先検証し、Windows Sandboxも候補とする |

#### Linux: Kata Containers

Kataは、コンテナを専用のゲストカーネルを持つVM内で実行します。まずLinux上のDocker＋Kata＋QEMUなど、確認対象の構成を一つに絞って検証します。

Kataの公式導入資料にはDocker連携があり、QEMUとの組み合わせで検証されています。一方、公式の制限事項にはPodman非対応とあるため、既存のDocker／Podman経路を一括で対応済みと扱いません。

Kataが動くことと、ゲスト側でmcp-writのLandlock／seccompが要求どおり効くことは別々に確認します。

#### macOS: Apple container / Containerization

Appleのcontainerは、Linuxコンテナごとに専用の軽量VMを起動します。基盤のContainerizationは、macOS側でVirtualization.frameworkを利用します。確認時点のcontainerの公式対応環境はApple silicon搭載Mac・macOS 26です。

これはmacOSのネイティブ実行経路とは別の追加方式です。Linuxゲスト内のLandlock等を、macOSネイティブのサンドボックスを適用した実績として数えません。ホスト側・ゲスト側の制御と既存経路との関係を明示し、利用者にOS固有事項を過度に負わせない導入方法を検討します。

#### Windows: Hyper-V分離コンテナとWindows Sandbox

Hyper-V分離のWindowsコンテナは、コンテナごとに最適化されたVMと独立したカーネルを使用します。Windows用イメージと起動処理を用意し、ゲスト内でも既存Windows版WardenのAppContainer・Job Object等が機能するかを検証します。現在のLinux用イメージに起動フラグを足すだけで成立するとは扱いません。

Windows Sandboxも、独立したカーネルを持つ使い捨てのWindows VM環境です。ただし確認時点の標準CLIである `wsb exec` はプロセスI/O非対応と明記されており、MCPの双方向stdio接続には中継等の検討が必要です。

Nano ServerはWindowsコンテナ用の軽量なベースイメージで、VM隔離方式そのものではありません。Nano ServerイメージをHyper-V分離で実行する場合、VM隔離を提供するのはHyper-V側です。軽量性だけで選ばず、Windows版ランナーと必要なAPIの互換性を確認します。

MicrosoftのMXCにもNanvixやHyperlight等の実験的なmicroVMバックエンドがありますが、MXCは早期プレビューで、現時点のプロファイルをセキュリティ境界として扱わない旨が明記されています。本計画では調査候補に留め、必須の保護をこれへ置き換えません。

### 方針・完了条件

- OSごとのネイティブ実行・サンドボックス経路を維持します。各方式でホスト側・ゲスト側に適用する制御と、併用できる範囲を明示します。
- 明示的に要求したVM隔離が利用できない場合、通常コンテナや非隔離実行へ暗黙に切り替えません。
- 実際に選択された実行方式、VMの分離単位、ゲストOS・カーネル、制御の適用状態をB2の結果へ反映します。設定値だけで適用成功とは判定しません。
- まず1サーバーを1VMに置く構成を検証します。同一VMや同一プロセスを共有する場合の境界は明記します。
- MCPのstdio通信、ポリシーの読み取り専用受け渡し、監査ログの保存、通常終了・強制停止・後始末が成立することを確認します。
- 必要なファイル共有、ネットワーク、資源制限を明示します。起動時間、メモリ使用量、導入・更新作業を測り、採用判断の材料にします。
- Auditorや監査ログがどこに置かれるかを記録します。ゲストカーネル侵害時も通信制御や監査を維持する保証が必要なら、VM外側に置く制御・ログ保存を別途設計します。

強化するのは、ワークロードとホストの間の隔離です。改善後も同一サーバー内の権限共有、MCP通信の通過規則、コード同一性の保証範囲、プロセス単位の履歴共有は残ります。

## B1. 実行対象OSを基準にしたポリシー受理

### 現状

コンテナ内がLinuxでも、コンテナ用ポリシーはホスト側ローダーを通ります。Windows向けビルドでは、Windows固有のネットワーク検査が適用されます。

### 方針・完了条件

ホストOS、実行対象OS、実行方式を区別し、実行対象を基準に受理・変換・検査します。ホスト側のマウント等の条件は、実行対象OSのポリシー受理条件と分けて確認します。

解消する問題は、ホストOSの制約が別OSの実行対象に混ざることです。実行対象をLinuxへ統一する必要はありません。対象のカーネル機能やマウント条件によって表現・適用できない制御は残るため、その差をB2へ出します。

根拠: [ホスト側のロード](../src/container/policy_export.rs#L36)、[Windows固有の検査](../src/policy/validator.rs#L498)。

## B2. この起動の適用予定・実効状態の可視化

### 現状

同じKDLでも、実行OS、実行方式、dry-run、劣化許容、欠落パスのスキップ、ホスト名規則をOS層で表現できないこと、任意のtrajectory等によって、実際に効く制御が変わります。

`allow_degraded` は劣化を許容する設定です。その値がtrueでも、実際には完全適用される場合があります。設定値と観測した適用状態を混同しません。

### 方針・完了条件

手順の簡素化と合わせて、この起動の制御を一つの結果として把握できるようにします。独立した別プロジェクトにはしません。

結果には、ホストOS・実行対象OS・実行方式、起動前の適用予定、起動時に確認できた適用状態、スキップした制御と理由、確認できない状態を区別して示します。A1のプロセス共通権限と、A5のVM隔離の状態もこの中で把握できるようにします。

解消する問題は、設定とこの起動で効く制御の関係が見えにくいことです。表示自体がOSで表現できる制約を増やすわけではありません。静的解析の未対応と検出ゼロの区別は維持し、生成ポリシーの判断材料として提示します。

根拠: [劣化許容と実際の適用判定](../src/warden/landlock_impl.rs#L271)、[OS別の制御範囲](guide.md)（698行）、[クライアント側転送](../src/auditor/proxy_c2s.rs)、[Pythonソース解析](../src/legislator/py_bind.rs)。

## C1. 応答内容のDLPとHTTP/SSE

応答の任意の文章・データに対するDLPと、HTTP/SSE対応は対象外とする製品境界を維持します。

A2で扱うメソッド、要求・応答の対応、応答内の追加要求などの仕様上の制御フィールドは対象に含めます。「応答内容は対象外」を理由に、これらの通過可否まで未制御にはしません。

この項目では製品境界の拡張は行いません。

根拠: [READMEのcontrol-planeの位置づけ](../README.md)、[対応MCP版の説明](guide.md)（657行）。

## C2. 手動CIの対象一覧と配布記述の整合

`workload_hash_e2e`、`environment_e2e`、`module_layering`、`manifest_fixtures` は、同コミットのワークフローの実行対象に含まれていません。`linux-tests` は `ci` が実行するinspector結合テスト3件を含みません。

手動起動の方針は維持します。ワークフローを変更する際は、各テストの実行担当と、実行対象に含めないものの扱いを明確にします。全ワークフローで同じテストを重複実行することを目的にはしません。

READMEの配布済みという記述と、実際の公開状況の整合は別途確認します。外部確認を行った場合は確認日と参照先を記録し、同コミットだけから導いた事実として扱いません。

解消する問題は、テストファイルとワークフローの対応・実行範囲が把握しにくいことです。手動起動方針は残り、この確認だけで全OS・全実行形態の動作を保証することもありません。

根拠: [ci.yml](../.github/workflows/ci.yml)、[linux-tests.yml](../.github/workflows/linux-tests.yml)、[platform-tests.yml](../.github/workflows/platform-tests.yml)、[container-tests.yml](../.github/workflows/container-tests.yml)、[mcp-servers.yml](../.github/workflows/mcp-servers.yml)、[go-runtime.yml](../.github/workflows/go-runtime.yml)、[workload_hash_e2e.rs](../tests/workload_hash_e2e.rs)、[environment_e2e.rs](../tests/environment_e2e.rs)、[module_layering.rs](../tests/module_layering.rs)、[manifest_fixtures.rs](../tests/manifest_fixtures.rs)。

## 改善計画を具体化する際の順序

1. **B1・B2を主計画として具体化する。** 実行対象の識別、ポリシー受理、適用予定・実効状態の報告を定義します。OS標準サンドボックス維持を受入条件に含めます。
2. **追加論点ではA1・A2を先に扱う。** 権限共有の説明と、MCPの通信手順を壊さない通過規則を固めます。
3. **A3で固定範囲と保証時点を明確にする。** 実行形態ごとの保証を区別します。
4. **A4で説明を揃える。** 一般化する場合だけ役割・パス抽出の設計へ進みます。
5. **A5の実機検証を、既存論点を置き換えない拡張として進める。** Linux、macOS、Windowsで検証済みの構成と未確認事項を分け、採用条件を満たす方式から追加します。

A5の調査・試作は主計画と並行できますが、既存の制御を省略してVMだけで安全性を説明する方向には変更しません。
