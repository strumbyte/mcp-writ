# ARM64解析対応と運用改善の作業手順書

作成日: 2026-09-18  
基準コミット: `cd8ebbf06badc5dc599aea3d3898d0f5e221d447`

本書は[作業計画](arm64-security-plan.ja.md)のD1とP0〜P8を実行するための手順である。
記載した新規モジュール・テスト名は配置案であり、基準コミットには存在しない。
コマンドの掲載は実行済みを意味しない。各段階の結果を末尾の様式で記録する。

## 共通ルール

- Pure Rustと依存の最小化を全モジュール・ビルド・テスト支援へ適用する。[全体の開発方針](development.md#dependency-and-ffi-policy)に従い、FFIは最後の手段とする。
- 依存の種類にかかわらず、機能・正確性・保証・対応環境・性能の後退は受け入れない。依存数を減らすために検査や解析範囲を削らない。
- リポジトリルートで作業する。既存のユーザー変更を保存し、作業対象以外を巻き戻さない。
- 日本語ファイルはUTF-8、BOMなし、LFで保存する。文字化けが疑われる場合は編集前に原本をバックアップし、原文を確認して最小差分で修復する。
- PowerShellで日本語を読み書きする場合は文字コードを明示する。Windows PowerShellの既定エンコーディングに依存しない。
- 実装変更と、それを説明する日英ドキュメントを同じ変更単位に含める。過去の評価文を根拠に現行仕様を書き換えない。
- 調査用サーバーは管理したfixtureを使う。dry-runやlive discoveryは実行を伴うため、実データや実サービスを検証材料にしない。
- テスト用の権限を広げて本来の制限を回避しない。未実施・skipは理由を記録し、実機合格と区別する。

## P0. 着手前の記録

1. 次の情報を取得し、基準コミットから実装が変わっていれば該当箇所を読み直す。

   ```sh
   git status --short
   git rev-parse HEAD
   git diff --stat
   rustc --version --verbose
   cargo --version
   ```

2. [開発手順](development.md)に従ってRustとPythonを用意する。Capstone導入時には、対象ごとのCコンパイラーとリンカーも記録する。
3. 変更予定の日本語ファイルを厳密なUTF-8として読み、BOMと改行を確認する。現状確認には `python3 scripts/check_docs.py` を使える。Windowsでは `py -3 scripts/check_docs.py`、または用意済みPython実行ファイルを明示して実行する。
4. 既存のx86 ELF fixtureについて、命令位置、解決番号、未解決、出力形式の基準結果を残す。比較対象のfixtureには元ソース、作成方法、ハッシュ、対象ABIを記録する。
5. 変更する領域の既存テストを実行し、変更前の失敗と環境不足を切り分ける。Inspectorは `cargo test --locked --lib inspector::`、運用改善は該当するAuditor・policy・Wardenのテストを使う。
6. 依存変更が影響する機能の要件と性能基準を記録する。起動、RPC中継・検査、ポリシー処理、バイナリ解析など該当する処理について、同じ入力・OS/CPU・ビルド設定で比較できる測定方法を用意する。時間・スループット・メモリと測定誤差の判定方法を先に定める。

**次へ進む条件:** HEAD、既存差分、変更前の機能・性能、使用できる実機と未検証項目が記録されている。

## D1. プロジェクト全体の依存削減

対象: `Cargo.toml`、`Cargo.lock`、全モジュールの依存使用箇所、
ビルド・テスト用スクリプト、CI・配布設定。
P0後に開始し、棚卸し結果をP4へ渡す。削減は対象ごとに分けて検証する。

1. 現在の依存グラフを記録する。次のコマンドはホストの設定が基準になるため、
   配布する各targetについても `--target` を指定して確認する。

   ```sh
   cargo tree --locked --edges normal,build
   cargo tree --locked --edges normal,build,dev
   cargo tree --locked --edges features
   cargo tree --locked --duplicates
   ```

2. `rg` とビルド設定を使い、依存ごとに利用箇所・必要な機能・有効なfeature・
   対象OS・直接/推移的依存・build/dev用途を記録する。
   lockfileの全エントリー数だけで実際の依存増減を判断しない。
   C実装、OSバインディング、外部ツールやテストランタイムも一覧に含める。
3. 未使用、役割の重複、複数バージョン、過剰なdefault featureを削減候補にする。
   標準ライブラリと既存依存で代替できるかを先に確認する。
   別のcrateや独自Rust実装に替える場合も、削減後の推移的依存と
   機能・性能・保守範囲を比較する。直接依存を推移的依存へ移しただけでは削減に数えない。
4. 一つの候補ごとにmanifestとlockfileを更新し、利用箇所と対象OSを検証する。
   テスト支援の削減でも検証範囲を失わない。
   変更が影響する振る舞いを確認できる既存テストを使い、必要な不足分だけ追加する。
5. P0と同じ条件で性能を比較する。依存削減と引き換えの速度低下・メモリ効率低下、
   起動遅延、解析機能の低下を認めない。再測定で誤差と退行を切り分け、
   条件未達ならその削減案を採用しない。
6. FFIが必要になる候補は、Pure Rust案で不足する要件と、
   改善を試みても解消できない根拠を記録する。
   実装の手軽さだけでFFIを選ばない。FFI案も同じ機能・性能条件で検証する。
   必須のOS APIへの境界は必要最小限のまま保ち、隔離機能を失う削除をしない。
7. 削減前後の直接・推移的依存、重複、feature、build/dev依存、
   ネイティブ依存・ツール、バイナリサイズとビルド時間を記録する。
   残す依存には用途と代替できない理由を記載し、比較だけに使った不要な依存を除く。

**完了条件:** 全体の棚卸しと削減候補の評価が完了し、要件を維持できる削減を反映した。
機能・性能・保証の退行がなく、残す依存と必要なFFIには根拠がある。
「一切依存しない」状態を作るために機能要件を変えない。

## P1. dry-runヘルプの修正

対象: [parse_run.rs](../src/cli/parse_run.rs)、[README英語](../README.md)・
[日本語](../README.ja.md)、[ガイド英語](guide.md)・[日本語](guide.ja.md)、
[ポリシー作成ガイド英語](policy-authoring.md)・[日本語](policy-authoring.ja.md)。

1. `noargs::flag("dry-run").doc(...)` を修正する。英語CLIの文言案は次のとおり。

   > Run the server without OS sandboxing; log and forward tool-call policy violations. Blocking tool-definition checks still apply. Server execution may have side effects.

2. 日本語の説明を次の内容に揃える。すでに同じ内容がある段落は重複追加せず、ヘルプへの導線や表現だけを最小限調整する。

   > OSサンドボックスを無効にしてサーバーを実行し、ツール呼び出しのポリシー違反を記録しながら転送します。ツール定義の遮断検査は引き続き適用されます。

   ファイル変更や通信などの副作用が起こり得ることも隣接して明記する。
   残存する遮断は設定に従うものであり、すべてのmanifest関連検査が無条件に
   同じ扱いになるとは説明しない。

3. 次を実行し、端末でヘルプを確認する。ヘルプ確認にサーバー起動は不要。

   ```sh
   cargo run --locked --bin mcp-writ -- run --help
   ```

4. 文言だけの変更に文字列を丸写ししたテストを増やさない。実装の挙動まで変更した場合に限り、違反要求の転送とツール定義の遮断に関する既存テストを再実行・補強する。
5. 文書チェックと `git diff --check` を実行する。

**完了条件:** ヘルプと日英説明から、dry-runが副作用のない検証モードではないと分かる。

## P2. OS別の保証範囲とSBPL依存の整理

対象: [Warden](../src/warden/mod.rs)配下、[policy validator](../src/policy/validator.rs)、
日英ガイド、日英ポリシー作成ガイド、[開発手順](development.md)。

1. 次の行を持つ対応表を日英ガイドに追加する。各セルを「OSで適用」「Auditorで検査」「拒否」「警告」「未適用」に分け、条件も書く。

   | 調査項目 | 必ず確認する点 |
   |---|---|
   | FS | globalとtoolの設定の関係、プロセス共通権限、OSの既定許可、書き込み・実行の扱い |
   | ネットワーク | ホスト名とTCPポートの違い、loopback、全許可・全拒否・限定許可の意味 |
   | syscall | Linuxのseccomp、他OSでの設定の扱い、per-tool指定の拒否 |
   | 適用失敗 | OS機構の不足、ポリシー拒否、明示的なdegraded設定、起動失敗 |
   | 非隔離実行 | dry-run、明示的なスキップ、未対応OSの分岐 |
   | 検証環境 | OS版、CPU、必要な権限、実行したテストと未実施の範囲 |

2. 基準コードの次の差を起点として確認し、変更後の実装に合わせて記述する。

   - LinuxのLandlockは許可されたtoolのFS権限もプロセスの規則へ合成する。per-toolの実行時隔離ではない。
   - Linuxのネットワーク規則はTCPポート単位であり、一般的なホスト名の固定とは異なる。変換できない設定をどう扱うかを確認する。
   - macOSのSBPLとWindowsのACL付与はglobalのFS設定を中心に構成される。Auditorで通ることだけではOSアクセス成功を保証しない。
   - macOSの限定ネットワーク設定はloopbackのポートを扱い、remote hostnameを拒否する。
   - Windowsは宛先ごとのoutbound allowlistを実現できないため、制限モードで非空allowlistを拒否する。
   - 明示的なper-tool syscall指定はvalidatorで拒否される。
   - 上記以外も含め、「未対応はすべて拒否」という表現で一括しない。

3. SBPLについて、Appleのサードパーティー向けサポート対象ではないこと、検証したmacOS版、OS更新時の再検証手順を書く。[Appleの説明](https://developer.apple.com/forums/thread/661939)を根拠として示す。新しい同意フラグは追加しない。
4. 既存のOS固有テストを確認し、表の根拠をコード・テスト・実測結果に対応付ける。未実施ならその旨を書き、実測値を推測で埋めない。
5. ガイドへ実際のKDL例と、拒否される場合のメッセージ例を追加する。例が現在のloader/validatorで成立することを確認する。

**完了条件:** ユーザーが設定を適用したときの各層の挙動と、未対応時の結果を判断できる。

## P3. 診断と実アクセス比較

### P3-A. 診断の分類

対象: [error.rs](../src/error.rs)、[runtime launch](../src/runtime/launch.rs)、
[runtime wait](../src/runtime/wait.rs)、[audit_log](../src/auditor/audit_log.rs)、
各OSのWarden実装、日英トラブルシュート。

1. 既存の型付きエラーと発生段階を棚卸しする。`LaunchError`、
   `WardenError::SandboxSetup`、`ProcessSpawn`を活用し、
   同じ原因情報を別の型や文字列解析で重複管理しない。
2. 診断を次の基準で整える。表示名やイベント名は既存の監査形式と整合させる。

   | 確定できる事実 | 表示する内容 |
   |---|---|
   | Auditorが要求を拒否 | 対応する要求ID、ルール、拒否理由。既存の秘匿処理を維持 |
   | ツール定義の検証で遮断 | manifest検証の結果。通常の引数違反と区別 |
   | サンドボックス設定・適用が明確に失敗 | OS、失敗した段階、元のエラー |
   | spawn失敗だが原因段階は不明 | 起動失敗と元のエラー。適用失敗と決めつけない |
   | 子プロセスのアクセスエラー・終了 | 観測できた終了状態。stderrやサーバーログを確認する案内 |

3. 子プロセスの `EPERM` / `EACCES` やstderr文字列だけを根拠に、
   「Wardenが拒否した」というイベントを生成しない。mcp-writが観測できない
   サーバー内部の失敗は、ログ取得できると約束しない。
4. Linuxの `pre_exec` では安全な処理だけを行うという既存条件を維持する。
   診断追加のためのアロケーションや複雑なログ処理をこの区間に持ち込まない。
5. 確定した設定失敗、一般的なspawn失敗、通常のファイル権限エラーを
   fixtureで分けて検証する。stdoutに診断文が混入しないこと、
   JSONL監査の形式と子プロセス終了処理を壊さないことを確認する。

### P3-B. Auditorと実アクセスの比較

対象: [pathutil](../src/pathutil.rs)、[checker](../src/auditor/checker.rs)、
[tool_enforcement_e2e](../tests/tool_enforcement_e2e.rs)、
[既存Rust fixture](../tests/fixtures/mcp_servers/open_path_server.rs)、
[既存Python fixture](../tests/fixtures/mcp_servers/open_path.py)。
必要なら `tests/path_resolution_e2e.rs` を追加する。

1. 一時ディレクトリに、許可対象A、同じプロセスで別用途に許可するB、
   OSポリシーの許可外Cを作り、それぞれ異なる識別内容を入れる。
   Cはサンドボックス適用前には通常のユーザー権限で読めることを確認する。
2. 同じJSON入力に対するAuditorの判定対象をテストから取得し、fixtureには
   その入力を元のまま渡す。必要な観測点はテスト用に限定し、
   本番ログへ機密パスやファイル内容を追加しない。
3. fixtureは本物のopenを行い、開いたハンドルに対する識別情報を返す。
   Unixのdevice/inode、Windowsのfile ID等、対象OSで取得できる値を使う。
   パスの再正規化結果や自己申告だけを実アクセスの証拠にしない。
   作成系は作成後のハンドルと親ディレクトリも確認する。
4. 既存Rust fixtureの簡易JSON抽出は、エスケープされたWindowsパス等の
   比較基盤としてそのまま流用しない。正しいJSONパーサーを持つfixtureを
   使うか、テスト用の抽出処理を改善する。Python/Node.jsはバージョンと
   パスの渡し方を明示し、ランタイム固有の変換も比較できるようにする。
5. 次のケースを、OSやファイルシステムの条件に合わせて実行する。

   | ケース | 期待する確認 |
   |---|---|
   | 絶対・相対パス、`.`、`..`、共通prefixの別ディレクトリ | 同じcwdで判定と実対象が一致するか |
   | 存在しない末尾、親だけ存在する作成先 | 最も近い既存祖先の解決と実際の作成先の関係 |
   | symlink、Windows junction/reparse point | 静的なリンク先と実対象。作成権限がなければskip理由を記録 |
   | 大文字小文字、区切り文字、Windows drive-relative/UNC/verbatim形式 | 実ファイルシステムとランタイムの挙動。UNCは管理した検証先だけを使う |
   | Unicode名、JSONエスケープ、file URI・URLエンコード | Auditorとサーバーがそれぞれ何をパスとして解釈するか |
   | 検査後のリンク差し替え | barrier等で順序を固定し、結果とプロセス権限の境界を記録 |

6. テストを三つに分ける。

   - **解釈比較:** 許可された同一入力が同じファイルに到達するか。不一致は再現入力と原因を記録する。
   - **OS境界:** Auditorが介在しない内部アクセスでもCへ到達できないか。OSの既定許可に入らないCを選ぶ。
   - **プロセス共通権限:** A用のツール経由で、サーバー内部の挙動によりBへ到達し得ることを設計上の制約として扱う。Wardenがツール別に拒否するという誤った期待値を置かない。

7. sleep頼みの確率的なレース試験を受け入れ条件にしない。
   最初は固定ケースと同期制御で再現性を確保し、その後に生成入力やfuzzingを追加する。
   再現した反例は固定の回帰ケースとして残す。
8. 既存テストを実行する。新規テストを追加した場合は、そのテストtargetを
   ローカルとCIの両方に明示的に組み込む。

   ```sh
   cargo test --locked --lib pathutil::
   cargo test --locked --lib auditor::
   cargo test --locked --lib policy::validator::
   cargo test --locked --lib warden::
   cargo test --locked --test integration --test tool_enforcement_e2e --test kdl_policy_e2e --test self_test
   ```

**完了条件:** 判定と実対象を比較した証拠があり、誤判定・OS制限・設計限界を区別できる。
既存の `generate-policy --self-test` の成功だけでこの条件を満たしたとは扱わない。

## P4. 依存の適合性比較と解析基盤の導入

対象: [Cargo.toml](../Cargo.toml)、[Cargo.lock](../Cargo.lock)、
[inspector](../src/inspector/mod.rs)配下、[inspectコマンド](../src/commands/inspect.rs)、
[generate-policy](../src/commands/generate_policy.rs)、[policy_generator](../src/legislator/policy_generator.rs)。

### 導入前の適合性比較

全体方針に従いPure Rust案を先に検証し、FFIは要件達成に不可欠な場合だけ許容する。
現時点の公開API調査だけで、Pure Rustが不可能、またはCapstoneが完全に適合すると
判定しない。代表的な命令列による小さな試作を、依存確定前に実施する。

1. 比較するcrateの版を固定し、`yaxpeax-x86 + yaxpeax-arm` とCapstoneに
   同じ入力・期待値を与える。ARM追加だけの評価とx86置換の評価を分ける。
   既存iced-x86はx86の比較対象として残す。
2. 次の表に、APIで取得できる情報、自前で補う処理、実測結果を記録する。

   | 要件 | 評価する証拠 |
   |---|---|
   | x86解析の維持 | 部分レジスタ、明示・暗黙・条件付き書き込み、制御フローによる停止 |
   | AArch64解析 | `w8/x8`・`x16`、定数構築、別名命令、書き換え時の未解決化 |
   | 不完全な情報の扱い | 未知の効果を副作用なしにせず、誤った解決済みを出さない |
   | 実用的な解析範囲 | 既存の解決可能ケースを失わず、代表的なARM64ケースを解決できる |
   | 性能 | 同一条件での解析時間・スループット・メモリ・起動負荷。測定誤差を超える後退がない |
   | 依存・ビルドと保守 | D1の基準に対する直接・推移的依存、feature、C依存、配布ターゲット、補完コード |

3. Pure Rust案が同じ受け入れ条件を満たせば優先する。満たせない場合は
   具体的な反例・不足情報・必要な補完範囲を記録する。補完コードが必要なことと、
   要件を実現できないことを混同しない。
4. Capstone側にも同じ試験を適用し、適合した場合にFFI採用を確定する。
   C側APIの説明をRustラッパーがそのまま保証すると仮定しない。
   両案に不足があれば補完処理や別案を検討する。機能・性能の要件を引き下げて
   選定を終わらせない。
5. 選定結果を作業計画へ反映する。以降のCapstone固有手順とP5〜P7は、
   Capstoneを採用した場合に実施する。Pure Rust採用時は該当手順を差し替え、
   共通の解析要件・受け入れ条件は維持する。

### 共通基盤と、Capstone採用時の導入

1. 入力形式・ISA・ABI・エンディアン・slice・コード範囲を表す型を設計する。
   配置候補は `src/inspector/target.rs`。入力の識別とホスト上での実行条件を分ける。
2. 解析状態と理由をprofileへ追加する。形式未対応、ISA未対応、ABI不明、
   コード領域なし、部分解析、破損入力、ネイティブ解析非適用を区別する。
   非x86 ELFを単なる空配列として返す経路をなくす。
3. 出力の互換方針を先に決め、human/JSON/KDLへ解析状態を追加する。
   既存フィールドの削除・型変更が必要なら移行方法を明記する。
   JSON/KDLを実際にparseするテストで新旧利用への影響を確認する。
4. リスク表示とポリシー生成へ状態を伝える。未解析を根拠に権限不要と断定せず、
   不明だから全許可にする処理も追加しない。生成物は要レビューの草案として、
   対象ABIと未解析範囲を示す。
5. iced-x86を薄い内部インターフェースに包む。配置候補は
   `src/inspector/decoder/`。共通化するのは必要な情報と不明状態だけにし、
   レジスタ別名や定数構築はアーキテクチャ固有処理へ残す。
6. Capstoneの採用版を選び、`Cargo.toml` と `Cargo.lock` を一緒に更新する。
   同梱Cコア、feature、ライセンスと配布時の表示義務を確認する。
   必要な詳細情報を省くdiet構成を避け、使用するISAだけを有効にする。
   依存追加時だけlockfileを更新し、その後の検証は `--locked` で行う。
   ラッパー呼び出しとバックエンド固有の型はデコーダ内部に限定する。
   既存の安全なRust APIで足りる箇所へ独自のraw FFIを追加しない。
7. 詳細情報を有効にした試作で、明示・暗黙・条件付きレジスタ書き込み、
   オペランド情報、分岐グループが取得できるか実測する。
   情報の欠落や取得失敗を「副作用なし」に変換しない。
8. 既存の配布ターゲットごとにCコンパイラーとリンカーを確認する。
   標準の同梱Cビルドを基本とし、実行環境に別途Capstoneの共有ライブラリを
   要求する形へ変えない。クロスビルドはRust target追加だけで完了とは扱わない。
9. x86 fixtureの結果が意図せず変わっていないこと、破損入力がpanicせず
   失敗として扱われることを確認する。過大な領域数・サイズにも上限と境界検査を設ける。

**完了条件:** 全体方針に沿う選定根拠、依存の差分、解析状態の伝播、既存x86の機能・性能維持の証拠が揃う。
Capstone採用時は、意味情報とC依存のビルド成立性も確認できる。
この段階ではiced-x86を削除しない。

## P5. Linux AArch64 ELF解析

1. ELFの `EM_AARCH64` と対象ABIを識別し、4バイト命令の整列・
   エンディアン・コード領域の境界を確認する。扱わない組み合わせは明示する。
   Linuxのsyscall名を使う根拠がない入力は、ABI不明として扱う。
2. Capstoneで `svc` を検出し、Linuxの `svc #0` とそれ以外を区別する。
   syscall番号を `w8` と `x8` の関係から追跡する。
3. 定数構築を小さく実装する。まず `movz` / `movn` / `movk` と
   確認済みの `mov` aliasを対象にし、幅・shift・上位bit・32bit書き込みによる
   zero extensionをテストする。`movk` の一部だけで全値が決まったと扱わない。
4. 未知の書き込み、条件付き更新、メモリ由来の値、呼び出し、分岐、
   デコード失敗に遭遇したら、対応する推論を未解決で止める。
   未対応命令を飛ばして古い番号を採用しない。スライスの命令数・バイト数を制限する。
5. Linux AArch64専用のsyscall番号表を追加する。元データの版・取得元・
   生成方法・ライセンスを残す。`libc::SYS_*` のホスト側定数を
   他ISAバイナリの解析用番号表として流用しない。
6. 既知の番号、表にない番号、未解決の番号を別に保持する。
   `read`、`write`、`openat`、`execve`等の小さなfixtureで期待値を確認する。
   ABI差を検証できるよう、同じ数値をx86とARM64へ与えるケースも用意する。
7. 生の命令列、最小ELF、実際のコンパイラー生成ELFの順に検証する。
   fixtureの生成元とハッシュを残し、解析テストではバイナリを実行しない。
   Linux AArch64実機での起動・Warden検証は別のテストとして実行する。
8. `inspect` の全出力形式と `generate-policy` を検証する。
   ライブラリ内のsyscall、動的な番号、コード領域外などの未追跡範囲を表示し、
   生成ポリシーは実行対象のLinux AArch64環境で強制モード検証する。

**完了条件:** ISA・ABIが正しい結果と、推論できない理由を出力できる。
命令検出が成功しただけで番号解決やポリシー生成も完了したとは扱わない。

## P6. Mach-OとDarwin ARM64解析

1. goblinを使って入力形式を振り分ける。ELF処理を維持し、
   Mach-O用のシンボル・文字列・コード範囲処理を追加する。
   配置候補は `src/inspector/macho_parser.rs`。
2. thin/fatのoffset・size・slice数・CPU subtype・対象プラットフォームを
   検証する。slice基準のoffset、ファイル基準のoffset、仮想アドレスを混同しない。
3. `__TEXT,__text`等の対象範囲を明示する。他の実行可能領域を扱えない場合は
   部分解析にする。fat入力はslice単位で結果を残し、ARM64だけ解析して
   universal全体が検証済みであるかのように表示しない。
4. インポート・シンボル・動的リンク情報を解析し、Mach-Oの名前表現を
   分類用に正規化する。表示や証拠用の元の名前は残す。
   libSystem等のラッパー呼び出しも検出対象とし、情報がstripped/bind形式等で
   取得できない場合はその範囲を記録する。
5. Darwinの `svc #0x80` と番号レジスタ `x16` を対象版のXNU資料と
   fixtureで検証する。Unix syscall、Mach trap、未知の入口を分ける。
   負のtrap番号を符号なし整数へ変換して、Linux syscall表に照合しない。
6. `inspect`、リスク分類、生成ポリシーの共通部分へ接続する。
   syscall番号・名称のOS/ABI情報を保持し、Darwinの検出結果を
   Linux seccompのルールへ出力しない。macOS側にないOS制御を生成できると
   表示しない。
7. Apple Silicon実機で、直接 `svc` を持つ最小fixtureと、
   C/Rust等から通常のライブラリを呼ぶfixtureの両方を確認する。
   解析試験と、SBPLによる実アクセス制限の試験を別々に記録する。
8. malformed Mach-O、切れたセクション、非対応slice、arm64e、
   未知ABIを検証する。非対応を0件・低リスクに戻さない。

**完了条件:** ARM64 macOSの解析対象と取りこぼす範囲が分かり、
既存のmacOSサンドボックス動作も維持されている。

## P7. x86比較とiced-x86置換の判定

1. 同じ内部インターフェースにCapstoneのx86-64バックエンドを実装する。
   比較用選択はまずテスト内部で行い、不要なユーザー向けフラグを増やさない。
2. 同一の入力を両バックエンドへ渡し、命令境界、syscall位置、番号、
   解決状態、重要なレジスタ効果を比較する。
3. 期待値を次の観点から独立して作る。両ライブラリの一致を正解そのものにしない。

   - `rax/eax/ax/al/ah`、zero/sign extension、条件付き書き込み。
   - `xchg`、`xadd`、`cmpxchg`等と、暗黙にレジスタを書き換える命令。
   - call、ret、条件分岐・間接分岐、デコード失敗、途中で切れた命令。
   - 可変長命令の境界、スライス開始位置、複数のsyscallとウィンドウ上限。

4. 差分を「既存の誤りの修正」「保守的な未解決化」「検出漏れ」
   「誤った解決済み」に分類する。従来正しく解決できたケースを未解決へ
   退行させる案は採用しない。既存の誤判定の修正は、命令仕様に基づく根拠を残して区別する。
5. 同一のfixture集合・ビルド設定・マシンで、解析時間、メモリ、
   配布バイナリサイズ、ビルド時間を測る。P0/P4で定めた方法で測定誤差と
   退行を切り分け、性能後退が確認された案は採用しない。
   起動時の差と大量ファイル解析の差を混ぜない。
6. 作業計画の採否条件を満たす場合だけiced-x86を削除し、lockfileと全配布ビルドを
   確認する。併用する場合は、両方が要件達成に必要である証拠と機能・性能維持の
   結果を記録する。比較用の不要な依存は残さない。

**完了条件:** 移行の可否が実測結果から説明でき、依存削除だけが目的になっていない。

## P8. 最終検証と配布準備

### 共通チェック

実装完了後、[開発手順](development.md)のチェックを同じコミットで実行する。
文書だけの変更では文書チェックと差分確認を行い、Rustテストは不要。

```sh
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo doc --locked --no-deps
python3 scripts/check_docs.py
git diff --check
```

Windowsの文書チェックは `py -3 scripts/check_docs.py` に置き換える。
rustdocはCIと同様に `RUSTDOCFLAGS=-D warnings` を設定する。
PowerShellでは専用セッション内で `$env:RUSTDOCFLAGS = '-D warnings'` とする。
オフライン実行は依存が取得済みの場合に限り `--offline` を追加する。

### OS・配布チェック

1. 作業計画の環境表に従い、実機テストとビルドだけの確認を分ける。
   Capstoneを使う解析fixtureは、ホストと異なるISAの入力も各OSで確認する。
2. 新規integration targetを [CI](../.github/workflows/ci.yml) と
   [Platform tests](../.github/workflows/platform-tests.yml)に追加する。
   現在のワークフローは明示したtargetだけを実行するため、ファイルを追加した
   だけではCIに載ったと扱わない。ARM64実行環境も明示して記録する。
3. [Release](../.github/workflows/release.yml)の全ターゲットで、
   C依存を含むビルド・リンクを確認する。対象OS上で配布物のhelp/versionと
   解析fixtureを動かす。Apple SiliconではRosetta実行とnative実行を区別する。
4. コンテナ対応に影響する変更では、互換性のあるLinux環境とDockerを用意して
   次を実行する。skipのまま合格させない。

   ```sh
   cargo build --locked --bins
   MCP_WRIT_REQUIRE_CONTAINER_TESTS=1 cargo test --locked --test container_e2e --test containerize_e2e --test wrap_image_e2e -- --nocapture
   ```

5. 既存のGo runtime検証も含め、リリース時の四つの検証ワークフローを
   同一コミットで確認する。通常のpush/PRで自動起動しない方針は維持する。
6. 日英README・ガイド・移行ガイド、[モジュール説明](modules.md)、
   開発・リリース手順のELF限定記載や依存要件を更新する。
   「実行可能なOS/CPU」と「解析可能な形式/ISA/ABI」を分けて掲載する。
7. `cargo package --locked --list` と配布アーカイブの内容を確認する。
   必要なライセンス表示を含め、実行環境で共有ライブラリが追加要求されないか確認する。
   公開操作は本書のチェックとは分け、実際のリリース時に[リリース手順](releasing.md)を使う。
8. D1の棚卸しを最終状態で更新し、全体の依存・feature・FFIの差分を確認する。
   影響する機能の性能測定と回帰確認を揃える。Pure Rust化・依存削減・FFI導入の
   いずれにも、機能・性能後退を例外として認めない。

### 差分・文字コードの確認

保存前に原文と変更予定の差分・保存形式を確認し、保存後に次を実行する。

```sh
git diff --stat
git diff --check
git diff -- docs
python3 scripts/check_docs.py
```

新規ファイルは通常の `git diff` に出ないため、内容を直接確認する。
原文を確認できない日本語を推測で書き換えたり、文字化けした節全体を
再生成したりしない。バックアップは配布物へ混入させない。

## 結果記録と切り戻し

各段階・実行環境について、次の様式で記録する。
本番の引数・秘密情報・ファイル内容を証拠へ混入させない。

```text
作業ID:
実施日 / 担当:
対象コミット / 未コミット差分:
OS・カーネル・CPU / native・emulation:
Rust / Cコンパイラー / リンカー / Python・Node.js:
Capstone crate・Cコア・feature / iced-x86:
Pure Rust候補の版 / 適合結果 / FFIが必要な場合の根拠:
直接・推移的依存 / feature / build・dev依存 / ネイティブ依存の増減:
機能の維持 / 性能基準・測定条件・測定誤差 / 比較結果:
fixture生成元・ハッシュ / 形式・ISA・ABI・slice:
検証コマンド / 終了コード:
期待値 / 実測結果:
結果: PASS / FAIL / SKIP / 未実施
証拠の保存先:
残る制約・差分の理由:
次段階へ進めるか / 必要な修正:
```

テスト成功だけで未実施項目を埋めない。OS/APIの非対応、権限不足、
Cツールチェーン不足はそれぞれ分けて記録する。
必須条件を満たせない項目は未完了として記録し、実装や環境を整えてから完了させる。
対応範囲を縮めたり性能要件を緩めたりして、条件を満たしたと扱わない。

切り戻し時は、原因となったバックエンドや出力変更の差分だけを戻す。
iced-x86を残している期間は既存x86経路を使い、新規解析対象は未対応と明示できる。
ポリシーの全許可化、dry-run化、degraded設定への変更を復旧策にしない。
共有作業ディレクトリに対して `git reset --hard` や無差別なcleanを実行しない。
