# mcp-writ 段階的リファクタリング計画

策定日: 2026-11-16。照合基準: `23d8e82764d3428e5f4bf719b3eba822c582cba1`、v0.5.2。

機能とセキュリティを維持しながら、要求処理・監査・DNS権限・起動処理を軽量化し、テストの重複と保守負担を減らす。境界条件の修正を先に行い、性能改善と構造整理を独立して評価する。各段階で検証と切り戻しが可能な状態を保つ。

本書は「何を、なぜ、どの順序で行い、何をもって完了とするか」を定める。変更ファイル、実装タスク、テスト名、コマンド、計測条件、実施記録は[リファクタリング実装手順書](refactoring-pr-guide-2026-11.ja.md)にまとめる。実装担当エージェントは両書を読み、担当するRF番号の手順に従う。

[従来の改善計画](archive/improvement-plan-2026-11.ja.md)と[従来の実装手順書](archive/improvement-pr-guide-2026-11.ja.md)は履歴資料である。過去の完了記録・測定値を本計画の完了根拠として転用しない。RF番号とRF-T番号は本計画固有の作業識別子で、過去のPR番号とは別である。

## 0. 照合の前提

| 根拠 | 策定時点で確認したこと | 未確認・再取得が必要なこと |
|---|---|---|

| 前回のWindows実行 | 合計2,681テストが成功。`audit_reopen_e2e`はWindowsでは0件 | Unixのreopenを含む対象OSでの実行証跡 |
| テスト一覧取得 | Windows既定featureで3,253登録。共通KDLの9ケースが25 targetに重複登録 | 一覧取得は実行成功の証拠ではない。前回実行とは取得範囲が異なり、件数の増減比較に使わない |

着手時は最新の差分を照合し、[モジュールの不変条件](modules.md)、[開発・検証方針](development.md)、[テスト担当と実行条件](test-matrix.md)を確認する。各作業は、必要な基準と前提が揃った時点で開始できる。全項目の計測完了を待つ必要はない。

## 1. 方針と維持する契約

特定のアーキテクチャ、protobuf、crate分割、行数やテスト件数の削減率を採用条件にしない。Rustの所有権と既存のモジュール境界を使い、実測と変更負担の減少を根拠に判断する。内部APIは見直してよいが、外部契約の意味変更は明示する。

| 対象 | 全作業で維持する契約 |
|---|---|
| 認可 | deny優先、server binding、未指定と明示的な空allowの区別、既存の許可・拒否結果 |
| MCP | raw IDと数値精度、重複キー拒否、対応version、MRTR、内部IDの秘匿、stdoutの用途 |
| tools/list | advertised全体の検証後に表示を絞る。再検証中の拒否と転送直前の世代確認 |
| セッション | confused deputy、trajectory、キャンセル後の未確定実行状態、件数・バイト上限 |
| 実行対象 | 開いた対象と実行する対象の同一性、spawn直前の確認、必要期間のpin保持、環境変数制限 |
| 監査 | 必要な永続化の成功前に保護対象を転送・公開しない。失敗ラッチ、ファイル同一性、親ディレクトリ同期、回転順序 |
| DNS権限 | 名前別TTL、protocol・port、TTL短縮、commit前の不可視性、トークン別rollback、資源上限 |
| OS管理 | cgroup・Job・PID namespace等の子孫管理、ACL復元、ハンドル回収、OS別shutdown動作 |
| 観測と解析 | intentとobservation、Unknownと成功、Partialと完全解析の区別 |

正常応答だけでなく、拒否理由・監査分類・終了コード・失敗段階・イベント順序・資源の残存を比較する。時刻やUUIDの差は対応付けて評価し、親子IDやreportとの相関関係は維持する。

## 3. テスト整理の対象と優先順位

目的は保証の重複と保守負担を減らし、有効なテストへ実行資源を配分することである。旧テストの入力・期待値・失敗検出をどの残存テストが担うかを対応付け、必要なOSとCIから到達できることを削除条件にする。

| 作業 | 優先度 | 対象・整理方針 | 実施順序・依存 | 主な完了条件 |
|---|---|---|---|---|
| [RF-T00](refactoring-pr-guide-2026-11.ja.md#rf-t00) 棚卸しと保証対応表 | 最初 | 登録・実行条件・保証・時間の一覧 | RF00に含める | 登録数、実行成功、skip、0件を区別し、移行先を特定 |
| [RF-T01](refactoring-pr-guide-2026-11.ja.md#rf-t01) 重複削除・assertion整理 | C | 共通KDL、trajectory、warden no-op、schema | RF-T00後。schema確認はRF05b前 | 固有の入力と失敗条件を残し、対象OSで確認 |
| [RF-T02](refactoring-pr-guide-2026-11.ja.md#rf-t02) 成功判定と実機検証の修正 | A | Windows sandbox、ACL復元、子孫管理、symlink前提判定 | RF-T00後、RF09前 | 起動失敗を見逃さず、実際の拒否・隔離・回収を確認 |
| [RF-T03](refactoring-pr-guide-2026-11.ja.md#rf-t03) target・fixtureの統合 | C | Inspector 3 target、純粋なself-test分類 | RF-T01後。Inspector部分はRF10の解析変更前 | 入力条件を維持して移動し、CIの実行先も更新 |
| [RF-T04](refactoring-pr-guide-2026-11.ja.md#rf-t04) fixtureビルド共有 | D | open-path fixtureの重複ビルド | RF-T00の計測後、RF-T02の判定方針に従う | 時間削減を実測し、単独・並行実行と成果物の信頼性を維持 |
| [RF-T05a](refactoring-pr-guide-2026-11.ja.md#rf-t05a) 実行0件のCI呼出し整理 | C | Go workflowのLinux専用lib test | RF-T00後に独立実施可能 | Linuxで実行し、WindowsのGo互換性検査を維持 |
| [RF-T05b](refactoring-pr-guide-2026-11.ja.md#rf-t05b) CI重複実行の統合 | D | 共通Linux検証の実行責任と結果参照 | RF-T01〜RF-T03のtarget構成確定後 | 同一SHA・必要条件の検証を一度は実行し、証跡がなければ実行する |
| [RF-T06](refactoring-pr-guide-2026-11.ja.md#rf-t06) launch失敗段階のfault-injection検証 | C | auditor起動失敗・stdio取得失敗等、自然誘発できない段階の注入検証 | RF09後 | 段階表の全失敗箇所に実行証拠があり、注入無効時の外部結果が不変 |

策定時のWindows条件では、共通KDLの集約と完全重複2件の削除により218登録を減らせる見込みである。最終件数の削減目標にはしない。追加すべき回帰試験を含めれば件数が増える場合もあり、登録数から時間短縮を推定しない。

認可、監査永続化、世代競合、ID精度、symlink、Unicode、OS隔離、ACL・子孫回収は保持する。対応済みMCP revisionと非対応versionの拒否、純粋な判定とwire／OSの実動作は別の保証として扱う。古い名称やphase番号だけを理由に削除しない。

## 4. 実施順序とPRの分割

| 段階 | 製品コード | テスト・検証基盤 | 次段階へ進む条件 |
|---|---|---|---|
| 1 基準取得 | RF00 | RF-T00 | 当該作業の入力、現行結果、実行条件を固定 |
| 2 正しさと検証の修正 | RF01・RF02・RF03 | RF-T01・RF-T02・RF-T05a | 問題を捉えるテストと修正後の実行証跡がある |
| 3 主要経路の改善 | RF04→RF05a→RF05b、RF06、RF07 | RF-T03 | 関連する修正がマージ済みで、保証と性能を比較できる |
| 4 責務分離と追加改善 | RF08→RF09、条件を満たしたRF10 | 条件を満たしたRF-T04・RF-T05b、RF09後のRF-T06 | 対象環境の保証が維持され、採用根拠が揃う |

段階は着手の目安であり、直接依存を満たせば独立した作業は先行できる。RF01〜RF03はテスト整理全体の完了を待たない。要求解析、監査、DNSの3系統は先行修正後に並行できる。共有ファイルを広く変更するRF08・RF09はマージ済みAPIを基準に進める。

新機能の実装は、優先度Aの作業（RF01〜RF03・RF-T02）の完了を前提にする。段階3以降は、新機能が変更するモジュールに関わる作業を先行し、それ以外は機能開発と並行するか後に回せる。優先度Dの作業は機能開発の着手条件にしない。機能開発と並行する場合、`checker.rs`・`forward.rs`・`launch.rs`等の共有ファイルは同時に編集せず、先にマージした側を基準にする。

テストの削除・移動、製品の挙動修正、性能改善は別PRにする。置換が必要なテストは代替を追加して対象環境で成功させてから旧ケースを除く。RF-T02で製品不具合が判明した場合は修正PRを分け、未検証の保証を前提にRF09へ進めない。RF10はCLI・framing・inspector・release設定を一つのPRにまとめない。

## 5. 性能評価と採否

| 計測 | 評価する範囲 | 主な指標 |
|---|---|---|
| M1 要求解析 | 正常・拒否・境界入力、大小フレーム、並行処理 | CPU、latency、throughput、allocation、メモリ |
| M2 ポリシー準備 | tool・schema・patternの規模差 | 準備、初回、定常処理、構築回数、常駐メモリ |
| M3 監査 | 通常・飽和、永続化方式、回転・終了 | 他タスクへの影響、同期開始と完了、drain、drop |
| M4 DNS権限 | grant数、期限切れ、集中・分散、並行予約 | lookup・commit、走査、lock保持、保持量 |
| M5 起動 | CLI、native、guest、pinとpayloadの差 | 初回応答、spawn準備、終了、残存資源 |
| M6 inspector | 対応形式・architecture、密な入力と打切り | 解析時間、parse回数、allocation、出力一致 |
| M7 buildと配布 | 対応target、clean・増分build | build時間、binary・配布サイズ、実行性能 |
| M8 テストとCI | 同じ保証集合と必須実行条件 | compile・link、warm実行、fixture構築、CI時間、資源使用 |

初期基準と各PRの直前親版を保存し、累積効果と当該PRの効果を分ける。同一host・toolchain・lockfile・profileで比較し、正常・拒否・境界の代表入力を固定する。初回とwarm、buildと実行、製品性能とテスト時間は分ける。入力、標本数、揺れの評価、比較方法は実装手順書で規定する。

機能とセキュリティの一致を先に確認する。性能改善は環境の揺れと区別できる実測を必要とし、再現する後退があれば見直す。保守性改善には速度向上を要求せず、非後退と責務・重複の改善を求める。RF01〜RF03・RF-T02の正しさを回復するコストは別記し、後続の高速化は同じ保証を備えた版同士で比較する。

全条件の直積や一律の高速化率は要求しない。削減効果が不明確なfixture共有・CI集約・release設定は保留できる。テストを実行しないことやセキュリティ検査を無効にすることを性能改善に数えない。

## 6. 判断事項

| ID | 論点 | 本計画の判断 | 別途判断が必要になる条件 |
|---|---|---|---|
| D-1 | 内部APIと外部契約 | 内部の型・所有権・データ構造は変更可能。MCP、KDL、hash、監査JSONL、reportの外部契約は維持 | 外部の意味・文言・終了コードを変える必要がある場合は差分を明示した別評価 |
| D-2 | schemaの準備と早期拒否 | 評価順序、最初のエラー、Fatalと不一致、エラー発生時点を維持 | 従来受理したschemaを新たな構築上限や先行検証で拒否する案 |
| D-3 | 監査の高速化 | 同期I/Oの実行場所を変えても、耐久ACK・順序・終了保証は維持 | group commit、同期頻度、公開前の永続化条件を変える案 |
| D-4 | キャッシュと共有 | 不変な解析・構築結果を対象とし、保持量を有界にする | mutableなファイル状態、権限、期限を再確認せず再利用する案 |
| D-5 | テストの削除 | 保証対応表、残存テストの実行、CI到達性を条件にする | 同値性が不明、代替が未実行、実機保証をmockのみへ置換する案 |
| D-6 | fixture・CIの共有 | 測定上の効果、成果物の信頼性、単独実行と欠落時fallbackを条件に採用 | artifactの由来・同一性や実行条件を確認できない共有 |
| D-7 | 追加の構造変更 | 実測と変更負担を根拠に必要箇所だけ採用 | アーキテクチャ様式、依存置換、panic方式、crate分割を目的とする変更 |
| D-8 | wslcのdescendant boundary不能基板 | `require_lifetime_boundary`がcgroup委譲・userns経路を持てないsubstrateではlaunchを拒否する現行fail-closedを維持 | 顧客環境で拒否が運用上問題になる場合の降格モードは製品仕様の変更として別途評価（§8の新機能に相当し、本計画の対象外） |

RF01の監査分類、RF02の重複予約、RF03の正しい順序は意図した修正として記録する。利用者向け仕様に変更が生じる場合は英語・日本語の利用文書も更新する。

## 7. 完了条件と切り戻し

各PRは、影響する契約と対象OSを特定し、実装手順書の共通検証と該当する回帰群を完了する。共有起動経路の変更では、実際に影響を受けるnative・container・VM等のbackendを検証する。0件、skip、unavailable、ignoredは実行成功に数えない。必要な環境がない経路は未検証として残し、完了扱いにしない。

完了記録には対象commit、変更と意図した入出力差分、テスト・環境・実行件数、測定条件と元データ、未検証経路、切り戻し先を記載する。テスト整理では旧新の保証対応表とselectorの移行証跡も残す。実装手順書のタスクを完了した時点で証跡を追記し、計画値を実績値へ読み替えない。

切り戻しはPR単位を基本とし、後続が新APIへ依存する場合は逆順で戻す。性能・構造変更を戻す際もRF01〜RF03の修正を含む版を基準にし、RF-T02で回復した失敗判定と代替検証は維持する。target・CIの構成を戻す場合はselectorとtest matrixも揃える。

監査workerやプロセスの所有権は稼働中のsessionで差し替えず、既存の終了手順でdrainと子孫回収を確認して切り替える。障害時に監査やsandboxを緩めて継続する変更は含めない。

## 8. 対象外

新機能追加、OS間の機能差解消、新しい隔離方式の導入、protobuf等への通信形式変更、特定のアーキテクチャ様式への統一は本計画に含めない。既存の内部構成や後方互換性を理由に不要な複雑さを残す必要はないが、利用者に見える契約の変更は本計画の内部整理と分けて判断する。

実装コマンド、変更対象の関数・テスト名、fixtureの境界条件、故障注入、OS別実行方法、採否の数値手順は[実装手順書](refactoring-pr-guide-2026-11.ja.md)を参照する。
